## PBT-gate note

This register is the contract for the **property-based-testing gate** on the §4.5
retrieval unit. The TestWriter's executed layer runs under `cargo test` with a
**deterministic pinned seed**, **≤100 generated cases per register row**,
**≤400 total cases** across the unit's whole property layer, **stop-after-5**
(report ≤5 distinct held/broken counterexamples per row), and records each row as
**held** or **broken** together with its `Strategy-id`. The adversarial reviewer
then reads this register with the executed artifacts and performs a **read-only**
PBT audit (per-row over-strength reasoning, generator-coverage check, prose
counterexamples, negative-generator requests); reviewers never run generators.

Authoring rule: `Property-id` = `P-<CLASS>-<N>`, `CLASS ∈ {IM, SM, TP}`, **≤ 8
rows**; invariants are **crisp, universally-quantified, black-box-observable
through the crate's public retrieval surface only**, and are **TRUE of the
current GREEN implementation** (implied by the green example suite — they are
**not** pending features). **There are no fail-state rows** (no `§6`/`FS-*`
rows) and **no gap/parked rows** — invariants only.

**Reserved-variant discipline applied.** Two decisions govern what this register
does **not** assert: **RESERVED-ERRVARIANTS-DISCIPLINE** — a reserved throw-path
is a fail-state that the current GREEN code does not construct (there is no
compressor/reranker/generation injection seam on `RagStore`), so `CompressionFailed`
(FS-17), `HyDEGenerationFailed` (FS-18), `RerankerUnavailable` (FS-16),
`EngineError`/`TraceUnavailable` (FS-9/FS-10), and **`MultiQueryExpansionFailed`
(FS-19)** are **reserved fail-variants, not properties** — no row depends on
them; the multi-query row below is scoped to "expansion **succeeds**" so it
never leans on the reserved `n>1-and-no-distinct-term` throw. **SUB-TASK-DAG-VALIDATED-ONLY** —
`subTaskDag` is an opt-in, SHOULD-HAVE surface whose `SubTaskDagFailed` (FS-26) is
a reserved fail-variant; the §4.5 green retrieval stack does not open the
sub-task DAG, so **no row exercises `sub_task_dag`**. Similarly, a `hybrid`/`vector`
query may surface the genuinely-wired `EmbeddingUnavailable` (FS-13) /
`VectorIndexUnavailable` (FS-14) when no provider/index is present; rows that touch
vector/hybrid legs are therefore scoped to a store that has a wired embedding
provider and a built vector index, and no row asserts "always empty" for a leg
that can throw.

## Property table

| Property-id | Class | Invariant | Strategy-id | Observable-as-property |
|---|---|---|---|---|
| `P-IM-1` | IM | **`rrf_fuse` output validity (unique, bounded, no fabrication).** For any list array `lists` and any `top_k ≥ 0`, the merged vector has **no duplicate `(DocumentId, NodeId)`**, its length is **exactly `min(top_k, #distinct keys in the input)`**, and **every** output key is present in at least one input list (nothing fabricated). | `strat:rrf-fuse` | ∀ generated `lists`/`top_k`: `merged = rrf_fuse(&lists, top_k)`; the multiset of `merged` keys is a set (all pairwise `!=`); `merged.len() == min(top_k, list of all-keys deduped length)`; `∀ (d,n) ∈ merged: ∃ list l, (d,n) ∈ l`. |
| `P-IM-2` | IM | **`rrf_fuse` determinism, outer order-independence, and EXACT tie-break ordering.** Repeating the call (and passing the same list array in **any permutation of the outer order**) yields the **identical output vector**; items with an **exact** RRF-score tie are ordered by `(documentId, nodeId)` ascending; the output is the top-`top_k` by descending RRF score (`RRF(d) = Σ_ℓ 1/(RRF_K + rank_ℓ(d))`, `RRF_K = 60.0`, 1-based rank), truncated to `top_k`. | `strat:rrf-ties` | For generated `lists`/`top_k`: `rrf_fuse(lists,top_k)` is element-wise `==` on a repeat and `== rrf_fuse(permute(lists), top_k)` for several permutations; re-deriving each output item's RRF score by hand from `lists` with `k = RRF_K` shows the output strictly non-increasing in score and, on exact ties, increasing in `(documentId, nodeId)`. **Exact-tie definition (pinned to the impl):** an "exact tie" means **equal ascending-canonical (sorted) sums of `1/(RRF_K + rank)` over the item's contribution multiset** — the executed oracle MUST sum each key's own contributions in the implementation's canonical ascending-sorted order (f64 addition is not associative; folding contributions in input/outer-list order is wrong and can flip the id-ascending tie-break). |
| `P-SM-1` | SM | **Result-set purity / wiki scope (no cross-wiki leak).** For a `rag_query` (any of `flat`/`graph`/`vector`/`hybrid`) with `wiki_id = A`, every returned `RagResultItem.document_id` belongs to wiki `A`; even when another wiki `B` holds identical content, no `B` document leaks into an `A`-scoped result, and no `B` item appears in the trace-derived leg order. | `strat:cross-wiki` | Seed wikis `A` and `B` with distinct documents (both indexable), wire `A`'s provider+index, query with `wiki_id = Some(A)` over all four modes: `∀ item ∈ result.results: owning_wiki(item.document_id) == A`; the same holds for `citations` and for every `(document_id,node_id)` key that appears in the multi-query/hybrid merged list. |
| `P-SM-2` | SM | **Graceful degradation on an empty / non-indexable wiki (deterministic legs only).** A `flat` or `graph` `rag_query` against a wiki with **no eligible indexable content** returns `Ok` with **empty `results` and empty `citations`** — never a panic, never a fabricated item, never a crash — and the returned `RagTrace` still has the correct per-mode shape. *(Reserved/unavailable-provider legs — `vector`/`hybrid` — are excluded here: they are allowed their wired `EmbeddingUnavailable`/`VectorIndexUnavailable` fail-states, which are reserved, not asserted.)* | `strat:empty-wiki` | For an empty-but-well-formed wiki (created via `create_wiki`) across `mode ∈ {Flat, Graph}` with a valid `top_k`: `rag_query(q, {wiki_id: Some(empty), mode, top_k})` → `Ok`, `result.results.is_empty()`, `result.citations.is_empty()`; `result.trace` is `RagTrace::Flat(..)`/`RagTrace::Graph(..)` respectively. A `flat` query on a wiki of documents whose text shares **no token** with the query also returns an empty `results` list. |
| `P-SM-3` | SM | **Full-query determinism / stability.** Repeating `rag_query(q, opts)` on an **unchanged** store returns a **element-wise identical** `RagResult` (same `results` including order and `score`, same `citations`, same `trace`, same `blocked_by`); `rag_stream(q, opts)` carries a `RagChunk::Result` equal to the `rag_query` result followed by `RagChunk::Done`. | `strat:repeat-query` | For a seeded multi-wiki multi-document store and a deterministic query+options (all modes; multi-query off or on; expansion succeeding): `r1 = rag_query(q,opts).await?`, `r2 = rag_query(q,opts).await?` — `r1.results == r2.results` element-wise (key, `score`, `parent`, `stale`, `source`), `r1.citations == r2.citations`, `r1.trace == r2.trace`, `r1.blocked_by == r2.blocked_by`; collect `rag_stream` chunks and assert the first is `RagChunk::Result(r)` with `r.results == r1.results` and the stream then yields `RagChunk::Done`. |
| `P-SM-4` | SM | **Dedup across fused legs / merged variants.** A `(documentId, nodeId)` appears **at most once** in a `RagResult.results` even when it is present in **multiple legs** of a `hybrid` query or in **multiple multi-query variants**; `citations` are likewise deduplicated across variants. The multi-query fan-out is **honest**: when it succeeds it merges only keys that exist in the scoped wiki, and repeated invocation is stable. | `strat:leg-overlap` | Build a store where one `(documentId,nodeId)` is simultaneously reachable by the `graph`, `vector`, and `lexical` legs (and seed it so a distinct expansion term exists when multi-query is on): `rag_query(q,{mode: Hybrid, multi_query:Some({enabled:true, n}), …})` → every key in `results` is distinct (`results` is a set), and for the disabled-multi-query hybrid run every merged key is distinct; `citations` contains no duplicate `(documentId,nodeId)`. |
| `P-TP-1` | TP | **Single-variant result-count bound.** For a **non-multi-query** `rag_query` (`multi_query` disabled or absent) with `compression = None` and `expand` either `None` or `Parent` (which preserves membership), the result length is **`≤ top_k`** and **≤ the number of distinct eligible items** in the scoped wiki — never more than either bound. | `strat:count-bound` | For seeded stores across all four modes with `multi_query` absent, `top_k ∈ {1, mid, ≥eligible}`: `result.results.len() <= top_k` and `result.results.len() <= distinct_eligible(wiki, filters)`. |
| `P-TP-2` | TP | **Compression is a pure projection (no invention / no reorder).** For a fixed query and store, the compressed result keys are a **subset** of the uncompressed (`CompressionMode::None`) result keys, preserving the input key set's order and identity; `CompressionMode::Extract` and `CompressionMode::Graph` are pass-through in the current GREEN retrieval stack, so their key set **equals** the uncompressed key set exactly. *(Compression never invents a key it did not see, never changes a `document_id`/`node_id` or their relative order, and `Filter` only *drops* low-relevance snippets. **`Filter`'s strict non-empty shrink (`keys(flt) ⊊ keys(base)`) is asserted, not just `⊆`, by a PBT probe.** **`Extract`/`Graph` `==` (pass-through) is currently implementation-grounded — both modes are pass-through in the GREEN retrieval stack; re-scope to a `⊆` invariant if real extract/graph compression lands.**)* | `strat:compression-project` | For a seeded store and a query with at least one on-topic and several off-topic eligible snippets: `base = rag_query(q,{compression:None, multi_query:absent}).results`; `flt = rag_query(q,{compression:Filter, …}).results`; `ext = rag_query(q,{compression:Extract, …}).results`; `gra = rag_query(q,{compression:Graph, …}).results` — `keys(flt) ⊆ keys(base)` (as a sub-***sequence***, preserving order); `keys(ext) == keys(base)`; `keys(gra) == keys(base)`. |

**Class tally:** IM ×2, SM ×4, TP ×2 = **8 rows ≤ 8** ✔.

## Generator-coverage note (per row — boundary + adversarial input shapes)

- **`P-IM-1 — strat:rrf-fuse`.** Empty `lists` (`[]`); a single list; `top_k = 0` (→ empty output); `top_k ≥` the distinct key count (→ full distinct set) and `top_k = 1`/mid (truncation across the score boundary); `top_k` larger than the corpus; **duplicate `(doc,node)` appearing in multiple lists**; the same `(doc,node)` repeated within one list; identical lists passed twice; a list containing keys not present in any other list (no fabrication: they may still appear if under `top_k`); `#distinct < top_k` (output length must equal the distinct count).
- **`P-IM-2 — strat:rrf-ties`.** Hand-construct exact ties with a **≥3-list** tie whose per-key contributions arrive in **non-sorted** outer order (the 2-list `[P,Q]/[Q,P]` case is commutative-safe — the order of two f64 additions does not change their sum — and cannot exercise the FP-non-associativity that flips the tie-break) and assert `(documentId asc, then nodeId asc)`; ties sharing the same `documentId` with different `nodeId`; ties across all three id axes; a large `top_k`; the same list array forwarded, reversed, and a random permutation as `permute(lists)`, each equal to the reference call; lists with duplicate inner elements (rank is positional, so swapping inner elements must change the score — the generator should confirm the property only claims **outer-array** order-independence, never inner-element permutation). The `rrf_fuse` **outer-order-independence** is regression-pinned by `tests/retrieval_stack_integration.rs::rrf_fuse_is_outer_order_independent_and_breaks_exact_ties_by_id` (the rrf_fuse host fix for FP-tie nondeterminism).
- **`P-SM-1 — strat:cross-wiki`.** Both wikis holding identical document titles/values (so a leak would be undetectable by content); a `B` document whose id sorts before an `A` document's id; a document moved/never shared; hybrid mode with legs reaching only `A`; a cross-wiki edge (`EdgeKind::Crosslink`) from an `A` doc to a `B` doc — assert the `B` target never surfaces in an `A`-scoped result; `graph` mode with `B` reference nodes that would be roots if scope were ignored.
- **`P-SM-2 — strat:empty-wiki`.** A freshly created empty wiki (no documents); a wiki whose documents have an empty graph (no indexable node text); a wiki whose node text shares no token with the query; `graph` mode on an empty wiki (no roots → empty, `blocked_by` stays `None` since nothing was blocked); `flat` mode on a document with only stop-word/whitespace text; `top_k` boundaries 1 and 50. Do **not** include `vector`/`hybrid` here (their missing-provider/index fail-states are reserved and out of scope).
- **`P-SM-3 — strat:repeat-query`.** Repeat each query twice with no intervening writes; repeat after an unrelated write to a *different* wiki (state unchanged for the scoped wiki); all four modes; multi-query enabled with a succeeding expansion; `expand: Parent` (parent payload must also be stable); `rag_stream` chunk sequence asserted to be `[Result, Done]` with the `Result` matching `rag_query`.
- **`P-SM-4 — strat:leg-overlap`.** A single reference node whose fact is also the top BM25 hit and a close vector neighbor, so the same `(doc,node)` is present in all three hybrid legs; multi-query `n ∈ {1,2,3}` with a distinct expansion term present; a `(doc,node)` seeded into multiple legs but that must still appear **once** in the merged output; citations duplicated across variants (dedup to one). Multi-query cases must only run where expansion **succeeds** (a `distinct` term exists) so the row never touches the reserved `MultiQueryExpansionFailed` throw.
- **`P-TP-1 — strat:count-bound`.** `top_k = 1` (tightest bound) and `top_k = 50` (max) and a mid value; a store whose eligible-item count `< top_k` and one whose count `> top_k`; `graph` mode whose resolvable target count `< top_k`; a hybrid store where every leg is full (assert the RRF merge caps at `top_k`); filters that shrink the eligible set. This row must set `multi_query` **absent/disabled** — the multi-query path may exceed `top_k` by fan-out, which is out of this row's scope.
- **`P-TP-2 — strat:compression-project`.** A query whose terms hit some snippets densely and others sparsely (so `Filter` drops a strict, non-empty subset); a query matching all snippets (Filter may be a no-op → still `⊆`, possibly `==`); a snippet with no token overlap (dropped); `Extract`/`Graph` pass-through on the same inputs (must be `==` to the uncompressed key set, in order); an empty result set under `None` (Filter/Extract/Graph also empty — projection trivially holds); repeat to confirm order preservation. Do **not** drive the compressor into its reserved `CompressionFailed` total-failure path (no seam, out of scope).

## API notes for the TestWriter

- **Pure helper.** `rrf_fuse(lists: &[Vec<(DocumentId, NodeId)>], top_k: usize) -> Vec<(DocumentId, NodeId)>` and `pub const RRF_K: f64 = 60.0` are `pub` in `src/retrieval/mod.rs` and **re-exported from `src/lib.rs`** (`pub use self::retrieval::{rrf_fuse, RRF_K};`) — rows `P-IM-1`/`P-IM-2` assert these directly and synchronously (`#[test]`, no runtime needed). Hand-derivation of expected RRF scores should use `k = RRF_K = 60.0` and 1-based rank (position + 1) per the pinned §4.5.3 rule.
- **Async surface.** `Store` implements `RagStore`; every retrieval method is `async` (trait returns `-> impl Future<…> + Send`; impls are `async fn`), so `P-SM-*`/`P-TP-*` rows await a `Result<…, StoreError>` under `#[tokio::test]`. Signature facts (current GREEN code):
  - `rag_query(query: &str, options: &RagQueryOptions) -> Result<RagResult, StoreError>` → `RagResult { query, results: Vec<RagResultItem>, engine: "gnosis", citations: Vec<(DocumentId,NodeId)>, trace: RagTrace, blocked_by: Option<Vec<BlockedBy>> }`.
  - `rag_stream(query, options) -> Result<RagStream, StoreError>` where `RagStream` yields `RagChunk::{Result(RagResult), Done, Error(StoreError)}`; on success the stream is exactly `[RagChunk::Result(rag_query(...) result), RagChunk::Done]`.
  - `bm25_search(wiki_id, query, top_k) -> Result<Vec<RagResultItem>, StoreError>`; `vector_search(wiki_id, query, top_k, provider, first_pass) -> Result<Vec<RagResultItem>, StoreError>`.
- **Build/seed the retrieval stack before vector/hybrid rows.** A `vector`/`hybrid` row needs (a) a wired embedding provider (`Store::set_embedding_provider(provider)`) and (b) a built vector snapshot (`Store::swap_snapshot(DerivedIndexes { vectors: Some(..), .. })` with `FieldType::Full` entries) — otherwise the leg throws the **reserved** `EmbeddingUnavailable`/`VectorIndexUnavailable`. The green example suites (`tests/retrieval_stack_integration.rs`, `tests/agent_memory_integration.rs`) have the sanctioned deterministic provider + index fixtures to reuse. `P-SM-1`/`P-TP-1`/`P-SM-3`/`P-SM-4` may use `flat`/`graph` (no vector needed) to keep some assertions dependency-free.
- **Wiki scope is `Option<WikiId>`.** `RagQueryOptions.wiki_id`, `bm25_search`/`vector_search` take a `&WikiId`. For wikiscope rows always pass `Some(A)`; a document's owning wiki is derivable through the public API (`get_document(did)` → `document.wiki_id`).
- **Options defaults/validation.** `RagQueryOptions` is `Default`; `top_k` default 10 and must be `1..=50`; `mode` default `Flat`; `max_hops` 1–5 default 3; `multi_query.n` default 3 but requires `n ≥ 1` when enabled; `compression` default `None`; `expand` default `None`. For **count-bound** (`P-TP-1`) keep `multi_query` disabled/absent; for **compression** (`P-TP-2`) keep it disabled and vary `compression` only. Always supply a `query` whose `trim()` is non-empty (empty → `ValidationError`, outside these invariant rows).
- **Determinism roots.** The `graph` and `hybrid`-graph legs collect reference roots from an unordered `HashMap`, so `Store` sorts roots by `(documentId, nodeId)` ascending before walking — this is why repeated queries are element-wise stable (`P-SM-3`). Each leg (lexical `lexical_rank`, vector `vector_leg`, RRF merge) sorts by score descending with ties broken by `(documentId, nodeId)` ascending.
- **Reserved-fail note for the generator.** Do not generate inputs whose success is impossible: (a) multi-query with `n > 1` on a wiki with **no distinct term** to fan out to → reserved `MultiQueryExpansionFailed` (exclude from `P-SM-4` by guaranteeing a distinct expansion term); (b) `hyde: true` does not open a fail-path in the current impl (generation is a deterministic stand-in and a provider embed failure is `EmbeddingUnavailable`, itself reserved) — prefer `hyde` unset/`false` in these rows; (c) `sub_task_dag` and reranker/compressor fail variants are reserved (SUB-TASK-DAG-VALIDATED-ONLY / RESERVED-ERRVARIANTS-DISCIPLINE) — no row exercises them.
