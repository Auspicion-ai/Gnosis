### 5.2 Critique findings (must-fix)

7. **The set never asks the one question §1–§3 depend on**: **is the engine to become the durable AUTHORITY at all**, or does the shell keep the authoritative store with an explicit **export/import seam**? Both branches are coherent; the set assumes the first without filing it. → §7 ruling (i).
8. **Durability's recovery target is unspecified** and is the design's core. `Store` carries shards, wikis, `next_id`, `reference_lock`, journal, `epoch`, communities, community-states, `fact_store`, `triple_store`, `state_annotations`, `entity_resolution`, `known_nodes`, derived snapshot, engine state, subsystem field, query audit log, embedding cache, provider slot (`src/store/mod.rs:1550-1732`). **`next_id` is `AtomicU64::new(0)`** (`:1697`) — under `ID-SCHEME-RECONCILE-MONOTONIC`'s "**never-reused**" (`docs/decisions.md:89`) **a bare counter snapshot is insufficient**; recovery must resume from the maximum allocated id. Snapshot-vs-journal-replay, format versioning, corruption fail-closed-vs-open, temp+rename-vs-torn-tail are all unanswered.
9. **Durability re-opens two ACTIVE decisions this set never names**: `SHARDED-RWLOCK-STORE` (no global lock, `docs/decisions.md:77`) and `IMMUTABLE-DERIVED-SNAPSHOT` (`:78`). A whole-store temp+rename collides with 64 independently locked shards; a journal-first design aligns with `WRITER-ACTOR-JOURNAL` (`:79`) instead.
10. **GRQ-2's commit token has no well-defined referent.** One request can append more than one journal entry (propagation and state-annotation appends are ordinary entries, `engine-wire-contract.md:667-669`, `:1409-1411`), so "the commit's change token" is ambiguous for a multi-append request. Pinning it would require defining a *request-scoped* token — a new concept, not a read of the existing cursor.
11. **Bulk ingest's three-way contract (atomicity / progress / cancellation) is internally inconsistent** and its failure vocabulary is closed. The §11 map stays 21 rows (`engine-wire-contract.md:727-736`); an over-cap outcome is therefore a **transport-level 413-class** outcome with its own register row (`docs/defects.md:47`'s disposition rule), not a new `StoreError`.
12. **Record-copy collides with the engine's monotonic id source.** Caller-supplied ids (`GRQ-6`) require either a **separate id namespace** or a documented precedence rule; the engine's source is `next_id` (`src/store/mod.rs:1556`, `:1697`).
13. **The durability self-report invites a self-reported claim.** A boolean the engine asserts about itself is exactly the false-claim class **U3 removed** from the six flags (`docs/decisions.md:98`; `get_engine_status`, `src/store/mod.rs:4193-4232`). The field must be **DERIVED** from configured write path, never stored.
14. **Notification: `edgeIds` has no identity encoding** (no `EdgeId` type in `src/`; `src/store/mod.rs:163-176`; `engine-wire-contract.md:639-641`), and the lossy contract is **already pinned** (`:678`, `:683-687`) — so GRQ-10 asks for a *decision this repo already made*.

### 5.3 Risk findings (a-big)

## 7. THE RULINGS

### (i) The durable-authority fork — the single decisive user question the set omits

**Ruling: this is the gate's primary finding, and it is for the user, not the gate.** The set assumes the engine becomes the durable authority (GRQ-1/§1, GRQ-5/§3, GRQ-6) without filing it. Two coherent branches:

- **Branch A — the engine becomes the durable AUTHORITY.** Then: **GRQ-1 is required** (a durable store is the authority's substrate); **GRQ-5/GRQ-6 are required** (the corpus must move); the shell's store becomes a **cache/consumer**; `docs/decisions.md:62-71`'s direction is confirmed and the unit is scheduled. **Cost:** the whole durability design (format/commit/recovery/restore semantics) + the O-8 authority switch + a two-authority window if sequenced wrongly.
- **Branch B — the shell KEEPS the authoritative store; the engine offers an explicit export/import seam.** Then: **GRQ-1 is unnecessary** (the engine is a rebuildable session cache); **GRQ-5/GRQ-6 become host-side or a thin import route** (the corpus never has to be authoritative engine-side); **GRQ-3's field becomes "cache" not "durable"**; the corpus-loss condition (`C-1`, **(C)**) is answered by export/import rather than by persistence. **Cost:** the engine is never the single source of truth; the consumer keeps the migration burden; the canonical `docs/specs/gnosis.md:102` ("Gnosis is the **persistence home** of documentation") and `:190` ("§4.1 Document store (**the persistence layer**)") + `:82` ("the doc-store persistence (nodes/edges) + revisioning") must be **reconciled**, and the user's prior answer to open question 4 (**YES — schedule a durability design unit**, `docs/decisions.md:62-71`) would have to be **reversed**.

**The gate's reasoning (not a fix — the direction this record recommends):** **Branch A** is what the canonical contract already states (`gnosis.md:82`, `:102`, `:190`) and what `ENGINE-DURABLE-CORPUS-DIRECTION` records as the user's answer; **Branch B** contradicts both and would require a user reversal. **But Branch A cannot land safely alone:** a durable engine store while the shell still holds the authoritative JSON store creates a **two-authority window**. **Therefore the ruling is:** **the durability design unit and the consumer's `SINGLE-WRITER-STORE`/O-8 amendment are ONE coupled decision, and the design unit may not be authorized before that amendment is recorded** — exactly GR-7's standing trigger (`docs/pending.md:97`). If the user wants durability **without** the authority switch, the engine's store must be explicitly labelled **"authoritative for nothing; the shell replays"** — a Branch-B variant that voids GRQ-1/5/6 as filed. **Single-source-of-truth invariant stated:** the shell may hold a **cache**; it may not hold a projection it outranks the graph with (`§4.2.7.2`; `GRAPH-OWNS-RELATION-AND-MERGE`, `docs/decisions.md:82`).

### (ii) The token question (cursor vs revision)

**Ruling: the standing refusal is restated and undisturbed; no new evidence was supplied.** The engine exposes **exactly one** wire-visible change cursor, defined as the decimal rendering of the committed journal `seq`, advancing by exactly 1 per committed journal entry, **process-lifetime monotonic**, scope = **cache invalidation / resync / de-dup ONLY** (`docs/decisions.md:97`; `engine-wire-contract.md:536-599`). **`GET /snapshot?revision=…` and `stale_revision` remain REFUSED** (`:576-584`). **What is genuinely owed** is **shell-side**: a consumer spec that **accepts the cursor** for what it is — no persistence across restarts, no cross-restart comparison, no validation/optimistic-concurrency use (`:568-571`) — and restates its stale-drop rule in the cursor's terms. **GRQ-4 and GRQ-11 are therefore DUPLICATE/OVERSTATED**: their remaining work is either the refusal's citation or a consumer document. **A genuine open sub-question the set raises and the gate answers:** *may the cursor ever become restart-stable?* **Yes — but only inside the durability design unit**, and only via an amendment that changes `:548-549` and `docs/decisions.md:97` **in the same unit**; the gate does **not** pre-authorize that change.

### (iii) The ingest / record-copy question

**Ruling: PARK-with-trigger restated, and the shape is narrowed to what the trigger can bear.**
- **Atomicity:** the trigger requires **one** answer; the gate's direction is a **single atomic route** (validate-then-commit-under-one-critical-section, mirroring `publish_document`'s validate-under-read-locks-then-single-shard-write pattern, `docs/decisions.md:83`), because "progress + atomic cancellation" cannot both hold (`docs/pending.md:95`) and a chunked design creates an engine-side **partial state** that becomes a second truth.
- **Cap:** an over-cap outcome is a **transport-level 413-class** outcome with its own register row — **not** a new §11 row and **not** a new `StoreError` (`engine-wire-contract.md:727-736`; `docs/defects.md:47`'s disposition rule).
- **Cancellation:** only meaningful for a **chunked** design; if the single-atomic route is chosen, cancellation reduces to "the request failed ⇒ nothing landed" — no `cancelled` terminal state is owed.
- **`{files:[paths]}` stays REJECTED** (`docs/HANDOFF.md:68`; `docs/pending.md:96`); a server-fixed corpus root or an inline-markdown body are the viable shapes.
- **`path`/segments stay PARKED** behind a **P1a wire-version decision** (the frozen `Document` body, `p1a §4.3:253-256`).
- **Record-copy (GRQ-6) folds into GR-6a's trigger**, with the **id-namespace question named as its own entry question** (caller ids vs `next_id`, `src/store/mod.rs:1556`, `:1697`).

### (iv) Status / health honesty

**Ruling: the `durability` signal is DERIVED, additive on `HealthReport`, never on `EngineSubsystems`, and lands WITH the store.**
